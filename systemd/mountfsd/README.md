# TLA+ model of dm-verity device sharing in systemd-mountfsd

Tree: systemd v262-rc2-60-ge96ff3b5b9.

`systemd-mountfsd` mounts images for unprivileged clients: a worker
process dissects the image on a loop device, sets up its dm-verity
device, creates the file system mounts, registers them with
`systemd-nsresourced` for the client's user namespace, and hands the
mount fds over.  With `veritySharing=true` the dm-verity device is named
after the root hash so that every worker mounting the same image shares
one device.  That is a protocol between the workers, the device-mapper's
deferred removal and udev's symlinks: `verity_partition()` opens the node,
activates the device or finds it exists, cancels the deferred removal
before it relies on the device, checks the root hash, waits for udev's
symlink, opens it, and re-arms the deferred removal when an attempt
fails or when it is done; after ten failed attempts it activates a
private device instead.

The model is that loop for a few workers, the kernel's open count and
`DMF_DEFERRED_REMOVE`/`DMF_DELETING` states of the shared device, udev's
symlink, and the client mounts that keep the device open.

## Running it

TLC ships in `tla2tools.jar` (https://github.com/tlaplus/tlaplus/releases,
version 2.19 was used).  Java 17 or newer.

    export TLA2TOOLS=/path/to/tla2tools.jar
    ./check.sh verity_fixed 8          # one configuration
    ./check-all.sh                     # every configuration, summary in logs/summary.txt

Every configuration finishes in seconds.

The runs above are in the foreground.  For anything that takes longer than a
coffee, start it detached so that it survives the terminal and the ssh session,
and check on it later:

    ./start.sh verity_fixed 32 32g          # like check.sh, detached: pid in logs/<cfg>.pid, output in logs/<cfg>.log
    ./run-parallel.sh 8 8g           # every configuration, each detached
    ./status.sh                      # what every run is doing (pass, violation, running, dead)
    ./resume.sh verity_fixed 32 32g         # a dead run continues from its last checkpoint
    ./summarize.sh                   # logs/summary.txt for fill-results.py

TLC writes a checkpoint every ten minutes into `/tmp/$USER-tlc-mountfsd/<cfg>/`
(`TLC_METADIR`, `TLC_CHECKPOINT`); `resume.sh` finds the newest one in the log.

## What is in the model

### Actions and the code they stand for

| Action | Code |
|--------|------|
| `Start`, `Loop` | `verity_partition()`: the attempt loop, `open()` of `/dev/mapper/<roothash>-verity`; ENOENT/ENXIO means "activate" |
| `Activate` | `do_crypt_activate_verity()`: the device is created (libdevmapper's udev cookie makes the symlink appear before the call returns), or EEXIST/EBUSY because it exists |
| `Check` | `dm_deferred_remove_cancel()`: EBUSY/ENXIO on a device that is being or has been removed, otherwise the mark is cleared and `restore_deferred_remove` set |
| `Reuse` | `verity_can_reuse()`: `crypt_init_by_name()` and the root hash comparison |
| `WaitLink` | `device_wait_for_devlink()`: the symlink appears, or the timeout falls back to a private device |
| `TryOpen` | the open after the activation or after the symlink appeared |
| `Opened` | success: the mount for the client, the worker's own fd closed, `decrypted_image_free()` marking the device for removal once the mount is gone |
| `Again`, `Fallback` | `try_again` and the end of the loop: the fd is closed, `restore_deferred_remove` re-arms the removal, the private device (not modelled) |
| `Die` | the worker is killed: the kernel closes its fd, no cleanup runs |
| `Umount` | the client unmounts |
| `RemoveWork`, `Udev` | `dm_deferred_remove()` taking the device away, udev processing the add and remove uevents |
| `Deactivate`, `Close` | `dev_remove` with `DM_DEFERRED_REMOVE` (open: mark; not open: delete now), `dm_blk_close()` (the last close of a marked device queues the removal) |

### Switches

| Constant | Meaning |
|----------|---------|
| `FIX_CANCEL_DEFERRED` | `dm_deferred_remove_cancel()` before reusing the device |
| `FIX_RESTORE_DEFERRED` | the `restore_deferred_remove` cleanup re-arms the removal when an attempt fails |
| `UDEV_SYNC` | the activation returns once udev created the symlink (libdevmapper's cookie); deferred removals carry no cookie, their symlink goes asynchronously |
| `WorkerMayDie` | a worker is killed in the middle of an attempt |
| `Workers`, `Attempts` | how many workers share the device, `N_DEVICE_NODE_LIST_ATTEMPTS` |

### Properties

| Property | Meaning |
|----------|---------|
| `OpenCountExact` | the device's open count is exactly the fds and mounts the model knows |
| `MountedIsActive` | a device under a mount is never removed |
| `NoOpenWhileDeleting` | nothing is opened on a device that is going away |
| `EveryWorkerFinishes` (liveness) | a worker that started finishes, with the shared or a private device |
| `NoOrphanDevice` (liveness) | once nobody is in the protocol and nothing is mounted, the shared device is gone |

Fairness is weak fairness on the workers, on the kernel's removal and on
udev.  A client's unmount and a worker's death are the environment's.

### Abstractions

- One image, one root hash, one shared device name; every worker asks
  for the same hash, so `verity_can_reuse()` only fails on a device that
  is going away.
- Activation creates the device or fails with EEXIST/EBUSY; the EINVAL and
  ENODEV quirks of libcryptsetup that the code also handles are not
  modelled.
- Removal is one step from `DMF_DELETING` to gone; udev handles one event
  per step and may take arbitrarily long.
- The private device of the fallback path is not modelled.

## What the model says beyond the code

- **`restore_deferred_remove` is only set on the reuse path.**  A worker
  that activated the device itself, could not open it and ran out of
  attempts leaves the device without deferred removal
  (`verity_no_udev_sync`).  With libdevmapper's udev cookie the open
  after the activation only fails if another worker's cleanup removed the
  device in between, and the next attempt goes through the reuse path,
  so the model finds no orphan with the cookie (`verity_fixed`,
  `verity_3workers`).  Without the cookie, or with more concurrent
  removals than attempts, the device stays behind until the next mount
  of the same image reuses it.  The systemd branch
  `work.systemd.mountfsd.deferred` sets `restore_deferred_remove` after a
  successful activation as well.
- A worker killed after `dm_deferred_remove_cancel()` leaves the device
  without deferred removal as well (`verity_worker_dies`); the cleanup
  is a `_cleanup_` variable and does not run on SIGKILL.
- Without `dm_deferred_remove_cancel()` the retries absorb the removals
  (`verity_no_cancel`): a worker that holds no fd while it waits for the
  symlink may find the device gone, and activates it again.
